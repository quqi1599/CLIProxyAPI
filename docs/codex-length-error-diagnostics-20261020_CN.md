# Codex 长度错误分类与诊断修复（2026-10-20）

## 已确认的问题

2026-10-20 按请求 ID 关联 NewAPI 与旧 CPA `2078cf6e9`：
`addd30da`、`78e2d403`、`14593a73`、`f5b25793` 的最终上游拒绝均为
`string_above_max_length` / HTTP 400。旧日志只保存错误码，没有保留
具体参数、限制值或实际长度，无法将这些历史请求归因到 `call_id`。
本次没有读取或重放客户原始正文。

本地合成上游进一步复现两个代码缺口：

- 这个确定的请求错误码不在 Codex 分类表中。HTTP 200 的 SSE / WebSocket
  流内长度拒绝会误归为渠道错误；当外层错误类型是 `server_error` 时，
  甚至 HTTP 400 也可能调用备用渠道。
- 上游错误安全摘要生成前没有提取受控的 `param`，后续用量报告和
  `failure_metadata` 日志无法定位被拒绝字段。

## 修改行为

### 确定的长度拒绝不重试

`string_above_max_length` 优先分类为 `InvalidRequest`、请求范围、HTTP 400，
不可重试；外层 `server_error` 不覆盖这个明确错误码。HTTP 握手拒绝、
SSE 和 WebSocket 终态沿用同一规则，保留真实外层状态和已经输出的状态。
既有 HTTP 413 请求过大分类保留原优先级。

WebSocket 无显式状态的终态原先固定写入 200；现在有本次握手状态时
使用实际状态（例如 101）。复用连接且没有新握手状态时保留已有状态来源，
不推断未观测到的握手结果。

### 只保留受控诊断

从分类器选中的同一个错误对象提取诊断，拒绝重复或转义后重复的 JSON 字段。
参数仅保留固定协议词表，数组下标归一为 `[]`，未知根字段舍弃，
自定义属性只保留可识别的父字段。例如：

- `input[2].call_id` → `input[].call_id`
- `tools[2].function.parameters.<自定义属性>` → `tools[].function.parameters`

诊断解析限制为 16 KiB、256 个 JSON 节点和 8 层嵌套；这些限制只决定
是否保留诊断，不改变请求或响应正文的业务范围。

错误码明确为长度拒绝，且完整匹配受支持的长度文案时，才记录上游报告的
最大值和实际值；数值范围为 0–1,000,000,000。文案没有明确单位就不记录单位，
不默认填入 64，也不从其他自由文本中猜测数字。诊断对象在复制和日志写入前
再次规范化，数值指针独立复制。

诊断经过 canonical failure、usage failure 和 usage reporter 进入原有
`failure_metadata` 文件日志：

| 字段 | 含义 |
| --- | --- |
| `upstream_error_param` | 受控参数路径 |
| `upstream_reported_max_length` | 上游明确报告的最大长度 |
| `upstream_reported_actual_length` | 上游明确报告的实际长度 |
| `upstream_length_unit` | 上游明确报告且被支持的单位；未知则省略 |

这些新增字段没有写入 usage 数据库，也没有新增数据库迁移。公开响应继续
使用安全摘要，不回显上游原文、自定义字段或客户内容。
